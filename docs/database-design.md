# 问卷系统 MongoDB 数据库设计

## 1. 设计目标

本系统使用 MongoDB 保存用户账号、问卷配置、提交回答和参与状态。数据库设计围绕问卷系统的实际业务和访问方式展开，主要考虑以下问题：

1. 问卷配置需要整体读取。 用户打开一份问卷时，通常需要同时获取标题、题目、选项、校验配置和跳转规则。
2. 回答记录会持续增长。 一份问卷可能不断收到新的回答，回答数据的增长速度与问卷配置不同。
3. 系统需要维护业务约束。 包括用户身份、问卷创建者权限、题目与问卷的归属、重复填写限制，以及答案的合法性。
4. 提交过程需要考虑异常。 参与记录和回答分开保存时，写入中断可能造成状态不一致，因此需要设计可恢复的提交机制。

基于这些需求，系统采用嵌入与引用相结合的方式，使用 `users`、`surveys`、`responses` 和 `participations` 四个集合分别保存不同生命周期的数据。设计重点不是把所有数据都放入同一种结构，而是根据数据之间的关系、读取频率、增长特点和一致性要求作出选择。

## 2. 集合与字段设计

以下列出各集合的主要字段、数据类型、用途和约束。`_id` 为 MongoDB 文档的唯一标识，项目中使用 `ObjectId`。字段是否必需、默认值和校验条件，应以当前 `init_schema.py` 与模型代码中的实际定义为准；对于会因业务场景而缺省的字段，在表中单独说明。

### 2.1 `users`：用户集合

`users` 保存注册用户的账号信息，为登录、问卷归属判断和参与身份识别提供依据。

| 字段 | 数据类型 | 必需性与约束 | 用途 |
|---|---|---|---|
| `_id` | `ObjectId` | 必需，唯一 | 用户唯一标识 |
| `username` | `String` | 必需、非空、唯一 | 登录用户名 |
| `passwordHash` | `String` | 必需 | 保存密码哈希，不保存明文密码 |
| `createdAt` | `Date` | 必需 | 用户注册时间 |

系统通过 `username` 唯一索引避免重复注册。密码以哈希形式保存，减少明文密码泄露的风险。用户信息没有嵌入每一份问卷或回答，而是通过 `ownerId`、`userId` 等字段引用用户 ID，避免在多个文档中重复保存账号信息。这样可以独立管理用户数据，但查询关联信息时需要由应用程序进行检查。

### 2.2 `surveys`：问卷集合

`surveys` 保存问卷的基本信息、题目列表及题目跳转规则。题目以嵌入式文档存放在 `questions` 数组中。

| 字段 | 数据类型 | 必需性与约束 | 用途 |
|---|---|---|---|
| `_id` | `ObjectId` | 必需，唯一 | 问卷唯一标识 |
| `ownerId` | `ObjectId` | 必需 | 问卷创建者的用户 ID |
| `title` | `String` | 必需，不能为空 | 问卷标题 |
| `description` | `String` | Schema 必需，可为空字符串 | 问卷说明 |
| `anonymousAllowed` | `Boolean` | 必需 | 是否允许匿名填写 |
| `allowMultipleResponses` | `Boolean` | 新建时应用写入，默认 `false`；旧文档可缺省时按默认规则处理 | 是否允许同一账号重复填写 |
| `status` | `String` | 必需；`draft`、`published` 或 `closed` | 问卷状态 |
| `deadline` | `Date` 或 `null` | 可选 | 问卷截止时间 |
| `questions` | `Array` | 必需，可为空数组 | 按顺序保存题目配置 |
| `createdAt` | `Date` | 必需 | 创建时间 |
| `updatedAt` | `Date` | 必需 | 最后修改时间 |

每道题作为 `questions` 数组中的一个嵌入式文档，主要字段如下。

| 字段 | 数据类型 | 用途与约束 |
|---|---|---|
| `_id` | `ObjectId` | 题目唯一标识 |
| `type` | `String` | 题型：`single_choice`、`multiple_choice`、`text` 或 `number` |
| `title` | `String` | 题目标题 |
| `required` | `Boolean` | 是否必答 |
| `order` | `Number` | 题目显示顺序 |
| `options` | `Array` | 单选题和多选题的选项；其他题型可省略，API 序列化时按实际实现返回 |
| `validation` | `Object` | 题目校验设置，如文本长度、数字范围或多选数量限制 |
| `jumpRules` | `Array` | 当前题目对应的条件跳转规则 |

选项通常由稳定的 `value` 和用于页面显示的 `label` 组成。答案和跳转条件使用 `value`，而不是显示文本。这样，即使之后调整选项显示名称，程序仍能通过稳定的值识别选项。`validation` 只保存当前题型适用的配置，例如文本题保存长度限制，数字题保存范围和整数要求，多选题保存选择数量限制。

### 2.3 `responses`：回答集合

每次成功提交问卷都会形成一条独立的回答文档。回答与问卷配置分开保存，避免回答数量增长时不断扩大问卷文档。

| 字段 | 数据类型 | 必需性与约束 | 用途 |
|---|---|---|---|
| `_id` | `ObjectId` | 必需，唯一 | 本次提交的唯一标识 |
| `surveyId` | `ObjectId` | 必需 | 所属问卷 ID |
| `respondentId` | `ObjectId` 或缺省 | 按匿名填写规则处理 | 填写者账号 ID；匿名回答不保存此字段 |
| `answers` | `Array` | 必需 | 保存本次提交的答案 |
| `submittedAt` | `Date` | 必需 | 提交时间 |

`answers` 数组中的每个答案包含 `questionId` 和 `value`。`value` 的数据类型取决于题型：单选答案通常为字符串，多选答案为字符串数组，文本答案为字符串，数字题答案为数字。服务端在保存前检查题目是否属于该问卷、答案是否符合题型规则，以及答案是否位于实际答题路径中。

将一次提交的所有答案放在同一份 `responses` 文档中，可以把这次提交作为统计和读取的基本单位；将不同提交分成多份文档，则可以避免问卷配置文档随着回答数量持续膨胀。

### 2.4 `participations`：参与记录集合

该集合用于控制禁止重复填写的问卷，并支持提交中断后的恢复。它保存参与状态及对应回答的关联信息，不作为普通问卷统计结果直接返回给创建者。

| 字段 | 数据类型 | 必需性与约束 | 用途 |
|---|---|---|---|
| `_id` | `ObjectId` | 必需，唯一 | 参与记录标识 |
| `surveyId` | `ObjectId` | 必需 | 对应问卷 ID |
| `userId` | `ObjectId` | 必需 | 登录用户 ID |
| `responseId` | `ObjectId` | 必需 | 首次提交对应的固定回答 ID |
| `status` | `String` | 必需；`pending` 或 `committed` | 标记提交处理状态 |
| `payload` | `Object` | 处理中暂存；完成后删除 | 保存首次接受且通过校验的答案，用于恢复 |
| `createdAt` | `Date` | 必需 | 接受提交的时间 |
| `submittedAt` | `Date`，可选 | 可选 | 首次回答的提交时间 |

系统对 `(surveyId, userId)` 建立复合唯一索引，保证同一账号对同一问卷只有一条参与记录。匿名回答不在 `responses` 中保存 `respondentId`，但参与记录仍包含登录用户 ID，用于防止重复提交。因此，本项目中的“匿名”表示问卷创建者无法直接从回答记录中查看填写者身份，并不代表数据库管理员无法通过参与记录关联身份。报告中应明确这一范围，避免将匿名填写描述为完全不可关联。

## 3. 嵌入与引用策略：设计理由和取舍

本项目没有将所有数据放在同一个集合中，也没有把每道题都拆成独立集合，而是根据数据关系、访问方式和增长特点选择不同的组织方式。

- 题目嵌入 `surveys`： 题目属于某份问卷，读取问卷时通常需要同时获取完整题目、选项、校验配置和跳转规则。将这些内容嵌入问卷可以减少额外查询，也便于草稿阶段统一维护题目顺序和配置。
- 答案嵌入 `responses`：一次提交中的答案通常需要一起校验、保存、读取和统计，因此放在同一份回答文档中，使一次提交对应一个清晰的数据单位。
- 用户、问卷和回答分开存储： 这些数据的生命周期和增长速度不同。用户账号相对稳定，问卷配置由创建者维护，而回答会随着提交持续增长。将回答放入独立集合，更便于按问卷查询和统计。
- 参与记录独立存储： 参与状态有自己的生命周期，需要记录提交是否正在处理、是否已经完成，以及发生中断时如何恢复。因此不只依赖 `responses` 中是否存在填写者字段来判断参与资格。
- 使用 `ObjectId` 建立逻辑引用： `ownerId`、`surveyId`、`respondentId`、`questionId` 等字段关联相关文档，避免在每份文档中重复保存整份用户或问卷数据。

这种设计的优点是问卷配置可以整体读取，回答可以独立增长，参与状态也能够单独管理；缺点是 MongoDB 不会像关系数据库外键那样自动检查这些引用，应用程序必须校验 ID、归属关系和权限。嵌入式题目还意味着问卷文档会随着题目增加而变大，因此不应把数量持续增长的回答也嵌入问卷。MongoDB 单个 BSON 文档有大小限制，设计时需要区分适合一起读取的配置数据与持续增长的业务记录。

## 4. Schema 校验与索引设计

### 4.1 Schema 校验

系统通过 `init_schema.py` 为集合创建或更新 MongoDB 校验规则。初始化时，如果集合不存在，则创建集合并设置校验规则；如果集合已经存在，则更新规则并继续初始化索引。重复运行初始化程序不会主动删除已有回答数据。

Schema 主要约束文档的基本结构、必需字段和 BSON 数据类型；题型相关的动态业务规则，例如必答检查、选项是否合法、文本长度、数字范围、题目归属、跳转目标和权限，则由服务端进一步检查。两层校验的作用不同：Schema 不能替代后端业务逻辑，前端限制也不能作为唯一的安全保障。

这种分层校验的优点是，错误数据可以在进入数据库时受到结构约束，同时复杂的题型规则仍能由应用程序按问卷配置灵活处理。代价是 Schema 与模型代码需要共同维护；如果只修改其中一处，可能出现数据库接受了结构上合法、但业务上不合理的数据。因此，初始化测试和业务校验测试都需要保留。

### 4.2 索引设计

| 集合 | 索引字段 | 类型 | 设计目的 |
|---|---|---|---|
| `users` | `username` | 唯一索引 | 防止用户名重复 |
| `surveys` | `ownerId` | 普通索引 | 加快查询指定用户创建的问卷 |
| `responses` | `surveyId` | 普通索引 | 加快按问卷查询回答和计算统计结果 |
| `participations` | `(surveyId, userId)` | 复合唯一索引 | 防止同一账号重复取得同一问卷的参与资格 |

普通索引主要改善常用查询的效率；唯一索引还承担数据完整性约束。索引会占用额外存储，并在插入、更新和删除时产生维护成本，因此本项目优先为常用查询条件和必须保证唯一的业务规则建立索引，而不是为所有字段都创建索引。

参与记录的复合唯一索引尤其重要。仅在应用层先查询“是否参与过”再插入记录，不能可靠处理并发请求，因为多个请求可能在写入前同时查到“尚未参与”。由数据库唯一索引进行最终约束，可以防止相同 `(surveyId, userId)` 参与记录被重复写入。

## 5. MongoDB 操作在系统中的应用

本项目不仅定义了集合结构，也在实际业务中使用 MongoDB 的插入、查询、更新、索引和 Schema 校验操作。

| 操作 | 项目中的使用方式 | 设计目的 |
|---|---|---|
| 插入（`insert_one`） | 保存用户、创建问卷、保存回答或参与记录 | 将新业务数据写入对应集合 |
| 查询（`find`、`find_one`） | 按 `ownerId` 查询用户创建的问卷，按 `surveyId` 查询回答，按 ID 查找问卷和参与记录 | 支持问卷管理、权限判断和结果读取 |
| 更新（`update_one` 等） | 更新问卷状态、题目配置和参与状态，处理待完成提交 | 维护业务状态，避免每次变化都重建整份文档 |
| 索引 | 用户名唯一索引、问卷创建者索引、回答问卷索引、参与复合唯一索引 | 提升常用查询效率并约束重复数据 |
| Schema 校验 | 初始化集合时设置或更新 `$jsonSchema` | 限制文档的基本结构、必需字段和字段类型 |
| 统计汇总 | 查询指定问卷的已保存回答，并在 Python 应用层汇总题目结果 | 计算提交数、选项选择次数及数字统计 |

当前统计逻辑由 Python 读取回答并在应用层汇总，尚未使用 MongoDB 聚合管道（如 `$match`、`$group`）。这种实现流程直观，便于用测试数据核对结果；但当回答规模增大时，应用层需要读取和处理更多文档。后续可以根据实际数据量评估是否使用聚合管道，把筛选和分组计算交给数据库完成。这里将其作为可改进方向，而不是描述为已经实现的功能。

## 6. 关键业务约束与数据一致性

1. 问卷归属： 只有问卷创建者可以管理自己的问卷和查看其统计结果。`ownerId` 用于建立归属关系，后端在管理操作中核对当前用户。
2. 状态与截止时间： 问卷状态包括 `draft`、`published` 和 `closed`。草稿允许配置；发布后锁定题目及关键填写设置；关闭或超过截止时间后，新的填写和提交会被拒绝。
3. 匿名与重复填写： 匿名设置和允许重复填写是两个独立选项。新问卷默认禁止重复填写；匿名回答不在回答文档中保存 `respondentId`，但参与记录仍可用于控制重复参与。
4. 答案有效性： 必答、选项数量、文本长度、数字范围、整数要求和实际答题路径由服务端校验，避免仅依赖前端数据。
5. 跳转规则： 规则作为问卷配置数据保存，由程序根据实际答案计算后续题目。服务端检查目标题目是否属于当前问卷，并在最终提交时再次验证答题路径。
6. 回答与统计： 每次成功提交形成独立的 `responses` 文档，统计结果从已保存的回答计算，避免单独维护一份容易与原始回答不一致的累计数据。
7. 提交恢复： 禁止重复填写时，系统先保存参与记录和首次通过校验的答案内容，再使用固定的 `responseId` 幂等保存回答，最后将参与状态更新为 `committed`。若中途发生错误，可以通过重试或初始化恢复待完成记录。
8. 恢复机制的边界： 该机制不等同于跨集合事务。系统依靠固定回答 ID、参与记录状态和幂等写入降低重复数据及答案丢失风险，但仍需要测试覆盖不同中断位置。
9. 历史数据： 初始化可以为可识别的历史非匿名回答补建参与记录，并保留原有答案；历史匿名回答缺少身份信息，不能据此恢复真实参与者，也不能声称可以追溯去重。

## 7. 嵌套结构与配置约束

下表进一步说明嵌入式配置中不同字段的作用及主要限制。

| 结构 | 字段与类型 | 约束或使用方式 |
|---|---|---|
| `options` 元素 | `value: String`、`label: String` | 选择题选项使用稳定值和显示标签；`value` 应唯一，答案及跳转条件使用该值 |
| 多选 `validation` | `minSelections: Int`、`maxSelections: Int` | 限制选择数量，需满足最小值不大于最大值，且不超过选项数 |
| 文本 `validation` | `minLength: Int`、`maxLength: Int` | 限制文本长度，最小值不大于最大值 |
| 数字 `validation` | `min` / `max: Number 或 null`、`integerOnly: Boolean` | 限制数值范围和整数要求；具体有限值及可保存范围由服务端校验 |
| `jumpRules` 元素 | `condition: Object`、`targetQuestionId: ObjectId` | 保存条件和目标题 ID；目标需属于当前问卷并符合跳转顺序规则 |
| `condition` | `operator: String`、`value: String 或 Number` | 单选使用 `equals`，多选使用 `contains`，数字按实现支持比较操作符；值类型需与源题型匹配 |
| `answers` 元素 | `questionId: ObjectId`、`value: String / Array / Number` | 答案与题目关联；正式提交只保存实际答题路径中合法且非空的答案 |

以下为简化的问卷文档示例，用于说明字段之间的关系。

```javascript
{
  _id: ObjectId("000000000000000000000100"),
  ownerId: ObjectId("000000000000000000000001"),
  title: "学习方式调查",
  description: "课程问卷示例",
  anonymousAllowed: false,
  allowMultipleResponses: false,
  status: "draft",
  deadline: null,
  questions: [
    {
      _id: ObjectId("000000000000000000000101"),
      type: "single_choice",
      title: "学习方式",
      required: true,
      order: 1,
      options: [
        { value: "online", label: "线上" },
        { value: "offline", label: "线下" }
      ],
      jumpRules: [
        {
          condition: { operator: "equals", value: "online" },
          targetQuestionId: ObjectId("000000000000000000000103")
        }
      ]
    },
    {
      _id: ObjectId("000000000000000000000102"),
      type: "text",
      title: "线下学习建议",
      required: false,
      order: 2,
      validation: { minLength: 0, maxLength: 1000 },
      jumpRules: []
    },
    {
      _id: ObjectId("000000000000000000000103"),
      type: "number",
      title: "年龄",
      required: true,
      order: 3,
      validation: { min: 0, max: 120, integerOnly: true },
      jumpRules: []
    }
  ]
}
```

示例省略 `createdAt` 和 `updatedAt`，实际问卷文档需要这些时间字段。题目在数据库中以 `_id` 保存，API 序列化时可转换为 `id`。`ObjectId` 引用只表示应用层关联，不代表 MongoDB 自动提供外键约束。

## 8. 设计理由、优缺点与后续考虑

本项目的数据库设计主要是在读取效率、数据增长、约束能力和实现复杂度之间进行取舍。

- 嵌入题目的优点是读取问卷时可以一次获得题目、选项和跳转规则，减少额外查询；缺点是问卷文档会随题目配置增长，题目更新也需要通过问卷文档维护。
- 独立存储回答的优点是回答数量增长不会不断扩大问卷文档，按问卷查询和统计也更直接；缺点是回答与问卷之间的引用需要应用层检查。
- 建立索引的优点是提升常用查询效率，并通过唯一索引维护关键约束；缺点是占用额外空间，写入时也需要维护索引。
- Schema 与业务校验分层的优点是数据库能够约束基本文档结构，后端可以根据题型和答题路径执行更灵活的规则；缺点是两层规则需要同步维护并通过测试验证。
- 参与记录与恢复机制的优点是能够控制重复填写，并在部分写入中断后尝试恢复首次接受的答案；缺点是增加了提交流程复杂度，而且跨集合写入仍需考虑中间状态，不能将其描述为完全等同于事务。

关系数据库也可以实现同一问卷系统，但通常会将问卷、题目、选项、跳转规则和回答分成多张表，再通过关联查询或应用层拼装。本项目依课程要求使用 MongoDB，并没有把每个业务实体机械地拆成独立集合，而是根据问卷配置的整体读取特点选择嵌入式题目，再将持续增长的回答和需要独立管理的参与状态分开保存。

## 9. 设计小结

本项目的 MongoDB 设计围绕实际业务访问模式展开：将问卷与题目嵌入保存，便于读取完整配置；将回答独立存储，适应提交记录持续增长和统计查询；通过参与记录及复合唯一索引控制重复填写，并使用待处理状态和幂等写入处理部分中断场景。Schema、索引和服务端业务校验各自承担不同职责，共同维护数据结构和关键业务规则的一致性。

开发过程也表明，数据库设计不能只看字段是否齐全，还需要考虑并发请求、异常恢复、匿名语义和后续统计需求。当前方案适合课程项目的功能规模，但仍需要通过持续的集成测试验证跨集合状态，并在数据规模扩大时评估聚合管道、分页查询等优化方式。
