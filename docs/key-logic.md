# 关键逻辑说明

本系统的关键逻辑主要包括条件跳转、答案校验、问卷状态与权限控制、回答提交与重复填写控制，以及统计计算。系统将题目配置和跳转条件作为数据保存，再由后端通用逻辑进行校验和执行，因此不同问卷不需要在代码中单独写死题目编号。

## 1. 条件跳转逻辑

跳转规则保存在源题目的 `jumpRules` 数组中，每条规则记录判断条件和目标题目。创建规则时，系统会检查源题和目标题是否属于同一份问卷，并要求目标题排在源题之后，避免跳回前面的题目形成循环。

目前支持的规则与题型如下：

| 题型 | 支持的操作符 | 判断方式 |
|---|---|---|
| 单选题 | `equals` | 答案等于指定选项的 `value` |
| 多选题 | `contains` | 所选答案中包含指定选项的 `value` |
| 数字题 | `equals`、`gt`、`gte`、`lt`、`lte` | 按数值相等、大于、大于等于、小于或小于等于判断 |
| 文本题 | 不支持 | 不能设置条件跳转 |

系统按照题目顺序处理回答，并按 `jumpRules` 数组中的顺序检查规则。若有多条规则匹配，采用第一条有效规则；若没有规则匹配，则继续下一道顺序题。如果已经没有后续题目，答题路径就结束。

跳转只决定本次填写实际经过哪些题目。被跳过的题目即使设置为必答，也不要求本次填写。为防止利用跳转绕过校验，服务端会从第一题开始重新计算实际答题路径，只校验路径上的题目，并拒绝客户端额外提交的、不属于实际路径的答案。前端显示的“已完成”状态不作为最终提交依据。

## 2. 答案校验逻辑

系统在保存题目配置时先检查配置是否合理；填写时再根据已保存的配置校验用户答案。前端输入限制主要用于改善交互，真正的答案合法性由服务端判断。

| 题型 | 主要校验规则 |
|---|---|
| 单选题 | 答案必须是字符串，且对应本题实际存在的选项 `value` |
| 多选题 | 答案必须是字符串数组；不能有重复选项；所有选项都必须有效；选择数量须满足最小值和最大值 |
| 文本题 | 答案必须是字符串；纯空白视为空答案；字符长度须符合 `minLength` 和 `maxLength` |
| 数字题 | 答案必须是有限数字；拒绝布尔值、NaN 和 Infinity；检查 `min`、`max` 及 `integerOnly` 要求 |

必答题不允许提交空答案。特别是必答多选题，即使 `minSelections` 的默认值为 0，空数组 `[]` 仍然会被拒绝，避免必答题被空数组绕过。非必答题可以跳过，但如果用户提交了非空多选答案，仍需满足该题配置的选择数量限制。

数字题会明确排除布尔值，因为在 Python 中布尔类型也属于整数类型。若设置只允许整数，`18` 和 `18.0` 都可通过，而 `18.5` 不通过。通过路径和答案校验后，空值、空字符串、空数组及纯空白文本不会作为有效答案保存，因此不会计入题目回答数或数字平均值。

## 3. 问卷状态与权限控制

问卷具有 `draft`（草稿）、`published`（已发布）和 `closed`（已关闭）三种状态，其行为如下。

| 状态 | 配置修改 | 填写 | 统计 |
|---|---|---|---|
| 草稿 `draft` | 创建者可以修改基本信息、题目和跳转规则 | 不允许填写 | 创建者可以查询 |
| 已发布 `published` | 题目结构和基本设置锁定；可设置截止时间或关闭问卷 | 截止前允许填写 | 创建者可以查询 |
| 已关闭 `closed` | 不允许继续修改或重新打开 | 不允许填写 | 保留历史结果供创建者查询 |

创建者权限由当前登录会话中的用户 ID 与问卷的 `ownerId` 比较确定，不能通过在请求中填写其他人的 ID 获得权限。问卷管理、发布、关闭和统计等操作均需检查创建者身份；草稿编辑接口还会检查问卷是否处于草稿状态。

系统要求用户登录后才能使用业务 API 填写问卷。`anonymousAllowed` 和 `allowMultipleResponses` 是两个独立设置：前者决定是否允许匿名提交，后者决定同一登录用户是否可以重复提交。两项设置默认均为 `false`，只能在草稿阶段修改，发布后锁定。

截止时间与问卷状态是分开的。截止时间到达后，问卷状态不一定自动变成 `closed`，但填写详情、逐题计算和最终提交都会检查问卷是否仍处于发布状态且尚未截止。即使逐题接口此前显示已经完成，最终提交时仍会再次检查状态和截止时间，防止问卷关闭或截止后继续提交。

## 4. 回答保存、重复填写与恢复

逐题填写接口只负责校验当前答案并计算下一题，不会保存正式回答。用户完成填写后，最终提交接口会从第一题重新计算答题路径，重新检查必答项、答案类型、跳转路径、匿名权限和问卷状态。只有实际路径上的答案全部通过校验后，系统才保存回答。

在禁止重复填写的情况下，系统通过 `participations` 集合记录用户对问卷的参与状态，并利用 `(surveyId, userId)` 复合唯一索引限制同一用户只能获得一条参与记录。仅先查询是否提交是不够的，因为并发请求可能同时通过查询；唯一索引可以在数据库层处理这种竞争。若该用户已经完成提交，再次提交会返回 `409`。允许重复填写时，每次合法提交都会保存为一份独立回答。

匿名提交时，回答文档不保存填写者的 `respondentId`；但系统仍使用参与记录控制重复填写。因此，匿名表示问卷创建者无法直接从回答记录中看到填写者身份，并不代表数据库层面完全不可关联。

参与记录和回答分别保存在不同集合中，不能将两次写入当成一个跨集合原子操作。为降低提交中断造成的数据不一致，系统采用可恢复流程：先保存 `pending` 参与记录及首次通过校验的答案内容，再使用固定的回答 ID 写入回答，最后将参与记录改为 `committed`。如果中途发生中断，重试或再次运行初始化流程时可以使用首次保存的内容继续完成，不会把后续重试中修改的答案覆盖为新内容。已经 `committed` 的参与记录不会因此生成第二份回答。

## 5. 统计逻辑

统计接口仅允许问卷创建者访问，并根据已经保存的回答计算结果。尚未完成保存的 `pending` 记录不作为正式回答参与统计。

| 统计内容 | 计算方式 |
|---|---|
| 提交总数 `responseCount` | 统计该问卷已保存的回答文档数量 |
| 题目回答数 `answeredCount` | 统计实际保存了该题有效答案的回答数量 |
| 单选题 | 统计每个选项被选择的次数，包括次数为 0 的选项 |
| 多选题 | 对每个被选中的选项分别计数，因此各选项次数之和可能大于回答数 |
| 文本题 | 返回已经保存的文本答案 |
| 数字题 | 返回有效数字答案，并计算平均值；没有有效数字时平均值为 `null` |

由于条件跳转会使不同填写者经过不同题目，各题的 `answeredCount` 可能不同。可选题被跳过时不会保存为空答案，也不会计入该题回答数。允许重复填写时，`responseCount` 表示提交份数，而不是独立填写人数。

当前统计逻辑由后端读取问卷回答后在应用层进行汇总，选项比例由前端根据计数计算。对于课程项目现有的数据规模，这种方式便于理解和验证；如果数据量明显增长，可以进一步考虑使用 MongoDB 聚合管道和分页优化。

## 6. 配置更新与调用边界

添加题目使用一次find_one_and_update更新管道，按当前题目数量计算order后追加完整题目，并返回实际保存的配置；$literal避免以$开头的用户文本被当作表达式。题目修改、删除和规则删除使用读取到的原questions数组作为更新条件，检测配置已变化时返回409，要求重新加载。这是配置快照的乐观检查，不是跨集合锁。

next的部分路径模式中，缺少题目键表示尚未作答，即使可选也在该题暂停；主动跳过需传键及null等空值。最终提交完整遍历，缺失可选题可以略过，必答题必须满足要求。next只计算不写回答，不能把它的完成标记当作提交凭证。

同一pending资格的并发恢复可能返回同一responseId的多个201，但固定_id只对应一份回答；已有committed资格再次请求409。重试仍先检查当前问卷及输入，问卷关闭或截止后通过初始化恢复此前已接受内容，没有后台自动定时恢复任务。跨集合存在中间状态，关闭、截止与回答写入之间也没有统一事务，不能宣称所有状态竞争都严格原子。
