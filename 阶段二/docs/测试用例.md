# 第二阶段测试报告

## 1. 测试目标

第二阶段在第一阶段问卷系统的基础上，新增独立题目、题目版本管理、题目共享、多题库管理和跨问卷统计等功能。本阶段测试主要验证新增功能能否正常使用，以及第一阶段已有功能是否仍然可用。

测试重点包括：
- 题目创建、复用和版本管理是否符合设计要求。
- 共享授权、撤销共享和不同用户之间的权限是否正确。
- 题目使用关系和跨问卷统计是否能够正常工作。
- 第一阶段的问卷创建、题目编辑、条件跳转、答案校验、提交和统计功能是否受到影响。
- 异常输入、版本冲突和数据库操作失败等情况下，系统能否正确处理。

本次测试结合自动化测试、MongoDB 集成测试、API 测试、浏览器自动化测试和本人进行的网页手动测试。

第五批首轮测试中，有3项测试没有通过。根据实施记录，问题出在故障注入测试没有作用于实际调用的数据库对象，导致测试预期的故障没有发生。
随后调整了测试替身和故障注入位置，重新运行测试，修复后的第五批累计 145 项测试全部通过。这一过程说明，测试失败时需要检查实际调用路径和测试环境，区分业务代码问题与测试方法问题，而不能仅根据失败数量判断系统功能存在缺陷。

## 4. 核心自动化测试用例

### 4.1 题目创建与复用

本项汇总两个独立自动化测试方法，每个方法使用自己的测试夹具；不是一次人工操作记录。

| 项目 | 内容 |
|---|---|
| 测试编号 | AUTO-01 |
| 测试目的 | 验证独立逻辑题目及初始版本创建成功，同一版本能在问卷中生成不同实例，回答仍按实例关联并保存可信来源 |
| 前置条件 | 测试客户端已登录；分别使用内存数据库替身或隔离的真实 MongoDB 测试库；测试数据由用例创建，不使用正式业务数据库 |
| 测试步骤 | 1. 发送下方创建请求。2. 在创建与读取用例中检查版本号、本人题目列表和详情。3. 在快照用例中创建标题为“快照测试”的问卷。4. 使用创建结果中的逻辑题目 ID、版本 ID，向同一问卷选题两次。5. 发布该问卷，为两个实例分别提交 18、20。6. 检查保存的答案及原有单问卷统计 |
| 输入 | 数字题“年龄”，必答，单位“岁”，范围 0～120，必须为整数；创建操作 ID 为 `operation-0001`。选题与提交请求见下方，所有资源 ID 使用接口实际返回值 |
| 预期输出：创建与读取 | 创建返回 201，初始版本号为 1；本人题目列表 `count=1`，详情返回 200；版本内容不包含问卷实例的 `_id`、`order`、`jumpRules` |
| 预期输出：复用与提交 | 两次选用生成不同的实例 ID，顺序为 1、2；使用指定来源版本；提交返回 201；首个已保存答案的 `questionId` 等于首个实例 ID，`sourceQuestionId` 等于原逻辑题目 ID；单问卷统计中首个实例的 `average=18`，不是将两个实例合并计算均值 |
| 实际输出记录 | 已有历史执行记录中，下列两个方法在 `InMemoryLibraryTests` 和 `RealLibraryTests` 中均为 `ok`，共四次执行。 |
| 测试结果 | 通过 |

**具体请求输入**

1. 创建逻辑题目：`POST /api/questions`。

```json
{
  "operationId": "operation-0001",
  "content": {
    "type": "number",
    "title": "年龄",
    "required": true,
    "validation": {
      "min": 0,
      "max": 120,
      "integerOnly": true
    },
    "unit": "岁"
  }
}
```

2. 创建问卷：`POST /api/surveys`，请求体为 `{"title":"快照测试"}`。
3. 两次调用 `POST /api/surveys/{sid}/questions/from-library`，每次请求体均为 `{"questionId":"{qid}","versionId":"{vid}"}`。
4. 调用 `POST /api/surveys/{sid}/publish` 发布，再调用 `POST /api/surveys/{sid}/responses`，请求体为 `{"answers":{"{iid1}":18,"{iid2}":20}}`。
5. 调用 `GET /api/surveys/{sid}/statistics` 检查首个实例的 `average`。

其中 `sid` 为实际创建的问卷 ID，`qid`、`vid` 来自题目创建结果，`iid1`、`iid2` 来自两次选题结果；花括号仅表示占位符，不是历史日志中保存的实际 ID。

**测试代码与结果说明**

- 提交的测试文件：[tests/test_library.py](../tests/test_library.py)。
- 创建与读取：`test_create_immutable_content_and_management_read`。
- 复用与回答来源：`test_snapshot_instances_distinct_and_answers_keep_instance_id`。

## 6. 测试结果分析

### 6.1 题目与版本管理

自动化测试覆盖了题目创建、版本历史、恢复和问卷快照等功能。测试结果表明，版本管理与问卷内题目实例可以分别处理，符合第二阶段保留历史内容和来源关系的设计目标。

### 6.2 共享与权限控制

共享相关测试覆盖了指定用户授权、撤销、重新授权、题库管理和权限隔离。已有测试通过，说明对应测试场景下的共享关系和访问边界符合预期。

### 6.3 跨问卷统计

跨问卷统计测试覆盖了使用关系、版本明细、统计配置和权限检查。统计结果需要依据有效来源关系及已提交答案计算，不能因为题目标题相同就自动合并所有历史数据。

### 6.4 第一阶段功能兼容性

第一阶段的问卷创建、题目管理、条件跳转、答案校验、提交和原有统计均有对应的回归测试。已有日志显示相关测试通过，说明这些功能在已覆盖场景中仍然可用。


## 7. 测试结论

根据现有历史测试日志，第二阶段第六批累计自动化测试执行 146 项，全部通过；另有 23 组浏览器自动化流程通过。开发过程中，第五批首轮出现的三项测试失败经过测试设置调整后，修复后的回归测试通过。本人也实际进行了题目创建与复用、版本管理、共享、多题库、跨问卷统计、不同账号权限隔离、异常提示及第一阶段功能等网页操作。

已有测试证据支持第二阶段主要功能在已覆盖场景下正常运行，并且第一阶段的核心功能在相应回归测试中保持可用。对于历史回答自动映射、跨用户统计授权、正式业务数据库及部分极端场景，仍需按照当前实现范围和实际验证情况如实说明。
