# AI 使用日志与使用说明

## 一、AI 工具与使用方式

本项目第二阶段在第一阶段问卷系统的基础上进行扩展，主要使用 ChatGPT 和 Codex 辅助完成需求分析、数据库设计、代码实现、测试和文档整理。

两种工具的使用侧重点有所不同：
- ChatGPT： 主要用于理解课程要求、讨论数据库设计方案、分析不同方案的优缺点、明确业务规则，以及整理项目文档。
- Codex： 主要用于检查现有代码、根据确定的设计方案分批修改代码、增加数据库模型和接口、实现前端页面，并通过测试检查实现情况。

本阶段没有直接使用 AI 重新生成一个完整系统，而是先讨论设计方案，再在第一阶段代码基础上分批实施，尽量保留原有功能和数据结构。

## 二、AI 使用日志

### 2.1 需求分析与总体方案设计

**使用工具：** ChatGPT。

**提示词：**

> 请根据数据库课程大作业第二阶段的需求变更，结合第一阶段已经实现的问卷系统，分析需要扩展的功能，说明数据库设计需要调整的地方，并提出能够保留旧功能的实施方案。

**AI 得到的内容：**

ChatGPT 帮助梳理了题目复用、题目版本管理、共享授权、个人题库、题目使用关系和跨问卷统计等需求，并分析了这些功能之间的关系。

**我的判断与修改：**

在讨论初期，我没有直接接受所有建议，而是继续询问不同方案的区别和实现代价。特别是考虑到第一阶段已经采用问卷内嵌题目的结构，我选择在原有结构上增加必要的数据关系和业务逻辑。

**最终形成的设计：**

第二阶段采用增量开发方式，保留原有问卷、回答、跳转和校验流程，并围绕题目复用和版本管理增加新的功能。

### 2.2 题目复用与版本设计

**使用工具：** ChatGPT。

**提示词：**

> 请比较题目复用方案 A（复制题目内容并保留原题 ID 和版本 ID）与方案 B（问卷只引用题目版本），结合现有问卷内嵌题目的结构，分析两种方案的优缺点。

**AI 得到的内容：**

ChatGPT 解释了两种方案在数据冗余、查询方式、历史问卷稳定性和原有代码兼容方面的区别，并通过题目内容修改的例子说明了版本管理的必要性。

**我的判断与修改：**

经过讨论，我选择方案 A。主要原因是第一阶段的问卷编辑、跳转、校验和提交逻辑已经直接读取问卷内的题目内容。如果完全改为引用版本，需要改造更多原有业务逻辑。随后，我继续追问题目内容变化是否需要创建新版本，以及问卷快照的含义，进一步明确了三个不同的标识：

- 问卷内题目实例 ID：用于问卷编辑、排序、跳转和回答关联。
- 逻辑题目 ID：用于表示题目的长期身份。
- 题目版本 ID：用于标识某一份确定的题目内容。

**最终形成的设计：**

从题库选择题目时，将选中版本的内容复制到问卷中，同时保存来源信息。问卷保留自己的题目快照，不会因为题库后续创建新版本而自动改变。

### 2.3 共享授权与题库管理设计

**使用工具：** ChatGPT。

**提示词：**

> 请比较指定用户共享和公开共享的区别，并结合课程提出的题目共享需求，明确题目所有权、使用权限、撤销共享和重新授权后的行为。

**AI 得到的内容：**

ChatGPT 帮助分析了不同共享方式对权限管理和系统复杂度的影响，并指出题目所有权与使用权需要分开管理。

**我的判断与修改：**

我选择指定用户共享，并进一步确定每个用户可以创建多个题库。对于撤销共享后的处理，我没有选择直接删除所有相关数据，而是决定保留题库条目和已有问卷快照，但禁止通过原共享关系再次选题。同时，我明确了版本权限：只有原题所有者可以创建原题的新版本，其他用户如果需要修改题目，应创建自己的副本。

**最终形成的设计：**

共享授权独立管理，撤销共享不会破坏已有问卷和历史记录，接收者也不会因为获得题目使用权而取得原题所有权。

### 2.4 统计兼容性与旧数据处理

**使用工具：** ChatGPT。

**提示词：**

> 请分析跨问卷单题统计的实现方式。如果同一道逻辑题目存在不同版本，题干、选项或校验规则发生变化，应该如何处理整体汇总、版本明细和历史回答？

**AI 得到的内容：**

ChatGPT 帮助分析了整体汇总、版本明细、统计兼容性和访问权限之间的关系，并指出题目来源相同不代表不同版本的答案一定可以直接合并。

**我的判断与修改：**

我选择同时支持整体汇总与版本明细，满足结构兼容条件后，由题目所有者明确确认是否合并对应指标。同时，我要求保留第一阶段的旧问卷和回答，不能仅凭题目标题相同就自动合并历史数据。

**最终形成的设计：**

统计时需要考虑题目来源、版本内容、有效答案和兼容规则。题目所有权也不等于查看其他用户问卷及原始回答的权限。

### 2.5 根据设计文档使用 Codex 分批实施

**使用工具：** Codex。

**提示词：**

> 请在现有第一阶段项目代码基础上，按照已经确定的第二阶段数据库设计和业务规则分批实施。每批明确修改范围，保留原有功能，补充必要测试，并根据实际测试结果修复问题。

**AI 得到的代码与修改：**

Codex 根据既定方案分批完成了以下工作：

| 批次 | 主要内容 | 结果 |
|---|---|---|
| 第一批 | 检查第一阶段代码结构、建立源码基线、明确修改范围 | 完成实施准备 |
| 第二批 | 实现逻辑题目、初始版本、题目来源和问卷快照 | 完成相关模型与接口 |
| 第三批 | 实现版本历史、版本恢复、分支和并发控制 | 完成版本管理功能 |
| 第四批 | 实现指定用户共享、授权撤销、重新授权和多题库 | 完成共享与题库功能 |
| 第五批 | 实现题目使用关系、整体统计、版本明细和兼容性管理 | 完成跨问卷统计相关功能 |
| 第六批 | 整合前端页面，增加题目库、版本、共享和统计的操作界面 | 完成前端整合及浏览器流程验证 |

**我的参与与修改：**

我先与 ChatGPT 讨论设计方案，再根据确定的设计文档让 Codex 分批实施。实施完成后，我结合测试记录和代码检查继续核对实现情况。

### 2.6 测试反馈与问题修复

**使用工具：** Codex。

**提示词：**

> 请检查当前测试结果，定位失败原因，区分业务代码问题和测试环境问题，修复后重新运行相关测试，并报告实际结果及仍未覆盖的情况。

**AI 得到的内容：**

Codex 根据测试反馈调整了部分实现和测试代码。例如，第五批首轮测试中，三个故障注入测试没有得到预期结果。根据记录，原因是测试注入没有作用于实际调用的数据库对象。调整测试替身和注入位置后，重新运行测试并通过。

第六批还针对浏览器测试、页面响应处理和时间显示等问题进行了调整。

**我的参与与判断：**

我将测试结果作为检查实现的重要依据，而不是仅凭页面能够打开就认定功能正确。测试失败时，需要结合实际调用路径和测试环境判断原因；测试全部通过时，也需要明确测试覆盖范围，不能将其等同于所有场景均无问题。

## 三、AI 使用说明

### 3.1 AI 帮助了什么

ChatGPT 帮助我理解第二阶段需求背后的数据设计问题。通过多轮讨论，我逐步理解了逻辑题目、题目版本和问卷题目实例的区别，也明确了题目共享、撤销授权、历史版本恢复和跨问卷统计之间的关系。

Codex 减少了逐个修改模型、接口、测试和前端页面的工作量。第二阶段涉及多个模块之间的配合，分批实施使我能够按照明确的任务检查每一部分，而不必一次性重写整个系统。

### 3.2 AI 的不足与需要注意的地方

AI 给出的方案和代码不能直接视为正确结果，仍然需要结合原有项目结构和实际测试进行检查。

在设计阶段，如果只关注新功能能否实现，容易忽略旧问卷、旧回答和原有题目 ID 的兼容性。因此，我通过继续追问方案的影响，逐步明确了问卷快照和来源字段的设计约定。

在实现阶段，测试结果也可能受到测试数据、数据库连接或测试替身设置的影响。第五批首轮出现的三个失败测试就说明，需要检查测试实际调用的对象和故障注入位置，而不能仅根据失败信息判断业务逻辑存在错误。

此外，AI 生成的设计说明不一定完全对应最终代码。题目来源、统计兼容和权限边界等内容必须以实际实现为准，不能把尚未实现或未经验证的设计写成已经完成的功能。

### 3.3 我自己的设计与判断

本项目并不是完全由 AI 自行决定设计方案。第二阶段的关键选择经过了我与 ChatGPT 的讨论和确认。我最终确定了以下设计：

1. 采用方案 A，将选中版本的题目内容复制到问卷，并保留来源关系。
2. 区分问卷内题目实例 ID、逻辑题目 ID 和题目版本 ID，保留第一阶段回答关联的含义。
3. 采用指定用户共享，每个用户可以建立多个题库。
4. 撤销共享后保留历史题库条目和问卷快照，但不允许通过原授权关系继续选题。
5. 只有原题所有者可以创建原题的新版本，其他用户通过创建独立副本进行修改。
6. 同时支持跨问卷整体汇总和版本明细，由题目所有者确认统计兼容性。
7. 保留旧问卷和回答，不自动根据题目标题合并历史数据。

我选择先理解课程要求，再与 AI 比较方案，继续询问不清楚的概念，最后根据第一阶段的实现结构和第二阶段的需求确认规则。

### 3.4 检查 AI 的实现结果

本阶段采用了自动化测试、真实 MongoDB 测试和浏览器流程测试等方式检查实现情况。根据现存实施记录，最终回归测试为 146 项全部通过；另有 23 组浏览器流程测试记录。第五批首轮测试曾出现三个失败，修复后重新运行并通过。第一批的 15 项数据库测试因连接问题被跳过，后续使用独立测试数据库进行验证。这些结果表明，现有记录中的相关测试场景通过了验证。

## 四、使用反思

通过第二阶段的开发，我认识到，使用 AI 完成课程项目并不只是让 AI 生成代码。更重要的是先把需求理解清楚，讨论数据结构和业务规则，再根据实际代码和测试结果检查设计是否真正落实。

本项目中，ChatGPT 帮助我逐步形成设计方案，Codex 则主要承担了分批代码实施和测试修复工作。我需要做的是理解课程要求、确定设计取舍、检查关键规则是否得到实现，并根据测试结果判断系统的实际完成情况。

这次经历也让我认识到，数据库设计会直接影响后续程序逻辑。例如，题目版本和问卷实例的 ID 如果没有区分清楚，就可能影响答案关联、跳转和跨问卷统计；共享授权如果没有独立管理，也难以正确处理撤销和重新授权。因此，AI 可以提高开发效率，但不能替代对数据含义、权限边界和历史兼容性的理解。
