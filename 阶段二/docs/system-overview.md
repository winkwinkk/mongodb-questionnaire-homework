# 系统说明

## 1. 项目简介

本项目是一个基于 Flask 和 MongoDB 实现的问卷系统课程项目。第一阶段完成了问卷创建与管理、题目配置、条件跳转、答案校验、问卷提交和基础统计等功能。第二阶段根据新的需求，在原有系统上扩展题目复用、版本管理、指定用户共享、多题库和跨问卷统计等能力。

第二阶段的目标是在保留第一阶段主要结构和功能的基础上调整数据库设计、扩展业务逻辑，并通过测试检查新增功能及旧功能的兼容情况。

## 2. 系统主要功能

系统功能可以分为以下几个模块。

| 模块 | 主要职责 |
|---|---|
| 用户管理 | 用户注册、登录和当前登录状态管理 |
| 问卷管理 | 创建问卷、编辑问卷信息、管理问卷状态和题目配置 |
| 题目管理 | 创建和维护问卷内题目，配置题型、选项、校验规则及题目顺序 |
| 条件跳转 | 根据当前问卷中的题目答案和跳转规则确定后续答题路径 |
| 答案校验与提交 | 检查答案格式和题目要求，并处理问卷提交 |
| 基础统计 | 查看单份问卷的回答结果和统计信息 |
| 题目与版本管理 | 维护逻辑题目、题目版本、版本历史及恢复操作 |
| 题库与题目复用 | 允许用户创建多个题库，将可用题目版本加入自己的问卷 |
| 题目共享 | 由题目所有者指定可以使用共享题目的用户，并管理授权状态 |
| 使用关系与跨问卷统计 | 查询题目被哪些问卷使用，并按整体或版本维度查看统计；统计合并需考虑版本兼容性和访问权限 |


## 3. 系统整体结构

系统采用浏览器页面、Flask 后端和 MongoDB 数据库的结构。页面负责接收用户操作并展示结果；后端路由接收请求并进行登录状态、参数和权限检查，再调用相应业务逻辑；数据库负责保存用户、问卷、回答以及第二阶段新增的题目管理数据。

```text
用户
 │
 ▼
浏览器页面与交互
 │ HTTP 请求
 ▼
Flask 应用与路由
 │
 ├── 用户认证与权限检查
 ├── 问卷和题目管理
 ├── 跳转、校验与提交流程
 ├── 题目版本、共享与题库逻辑
 └── 使用关系与统计逻辑
 │
 ▼
MongoDB
 ├── 第一阶段业务集合
 └── 第二阶段新增的题目管理及辅助集合
```


## 4. 后端模块职责

后端按路由、模型和业务逻辑等职责组织代码，避免将所有处理过程集中在单个文件中。

- **路由层**：接收 HTTP 请求，读取参数，检查登录状态和操作权限，并返回响应。
- **模型与数据访问层**：封装与 MongoDB 文档相关的读写操作，处理集合中的业务数据。
- **问卷与题目逻辑**：维护问卷题目、题目顺序、跳转规则和题目配置。
- **答题流程与校验逻辑**：根据当前问卷快照判断答题路径，检查答案是否符合题型和校验要求，并处理提交。
- **第二阶段题目管理逻辑**：处理逻辑题目、版本、共享授权、题库条目、题目使用关系和统计兼容性等业务。
- **数据库初始化与测试**：配置集合校验规则和索引，并通过自动化测试检查基础行为和回归情况。


## 5. 第一阶段与第二阶段的关系

### 5.1 第一阶段的基础设计

第一阶段主要使用 `users`、`surveys`、`responses` 和 `participations` 四个业务集合。问卷题目嵌入在 `surveys.questions` 中，回答通过问卷内题目实例 ID 关联题目。该结构便于一次读取问卷及其题目，也支持原有的跳转、校验、提交和单份问卷统计流程。

### 5.2 新需求带来的问题

当题目需要跨问卷复用、保存多个历史版本并共享给指定用户时，只依赖问卷内部嵌入的题目结构就不够方便。系统还需要回答：某道题由谁拥有、当前有哪些版本、谁被授权使用、哪些问卷采用了哪个版本，以及不同版本的回答是否适合合并统计。

### 5.3 第二阶段的扩展方式

第二阶段增加独立的逻辑题目、题目版本、共享授权、题库和题库条目等数据结构，并使用相关辅助记录支持版本操作或统计配置审计。与此同时，问卷仍保存题目快照，而不是改成只引用题目版本。

这意味着题库负责管理可复用题目及其版本，问卷负责保存自己实际使用的题目内容。题库后续更新或共享授权撤销，不应直接改写已有问卷快照。原有问卷内题目实例 ID 仍用于问卷编辑、跳转和答案关联，逻辑题目 ID 与版本 ID 用于来源追踪、版本管理和统计分组。


## 6. 主要设计考虑

### 6.1 保留原有答题结构

继续将题目内容嵌入问卷，可以让已有答题流程读取问卷自己的题目配置，减少对第一阶段功能的整体改造，也能让历史问卷保持稳定。

### 6.2 将可复用题目与问卷实例分开管理

逻辑题目和版本用于管理可复用内容；问卷内题目实例用于描述某份问卷中的具体题目。分开管理可以支持跨问卷复用，同时避免把不同问卷中的题目实例误认为同一个对象。

### 6.3 权限按业务对象区分

题目所有权、共享使用权、问卷管理权和回答查看权并不相同。允许某个用户使用共享题目，不代表该用户获得原题所有权；题目所有者也不能仅凭题目所有权查看其他用户问卷中的原始回答。

### 6.4 统计需要考虑版本语义

同一逻辑题目的不同版本不一定具有完全相同的题干、选项或校验含义。因此，跨问卷统计不能仅凭逻辑题目 ID 自动合并所有数据，还需要考虑版本兼容性、统计权限和有效答案口径。

## 7. 设计的优点与局限

该设计在保留原有问卷结构的同时，增加了题目复用、版本历史和共享能力。问卷快照有助于保持已创建问卷的稳定性；独立的题目与版本记录则便于追踪题目来源和历史变化。

相应地，题目版本与问卷快照中可能保存相似内容，需要明确它们各自的职责；共享授权和版本并发增加了权限检查与异常处理的复杂度；跨版本统计也需要判断不同版本的语义是否兼容。此外，第一阶段旧数据可能没有来源版本信息，因此不能只凭题目标题相同就自动关联或合并历史统计。
