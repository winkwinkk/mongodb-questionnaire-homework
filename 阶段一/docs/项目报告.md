# 基于 MongoDB 的在线问卷系统第一阶段项目报告

GitHub 代码仓库：https://github.com/winkwinkk/mongodb-questionnaire-homework

## 一 项目目标与需求分析

### 1.1 项目目标

本项目旨在设计并实现一个基于 MongoDB 的在线问卷系统，完成从用户注册登录、问卷创建、题目配置、条件跳转、问卷发布，到用户填写、回答提交和统计结果查看的完整业务流程。

本阶段重点解决三类问题：一是如何组织用户、问卷、题目和回答数据；二是如何根据不同答案执行可配置的跳转和校验；三是如何保证提交权限、重复填写控制及统计结果符合规则。项目采用 Python 和 Flask 实现后端，使用 MongoDB 保存业务数据，并完成配套网页、测试用例及 AI 使用记录，为第二阶段继续扩展保留基础。

### 1.2 需求分析

系统中的注册用户既可以创建问卷，也可以填写其他用户分享的问卷。创建者只能管理自己的问卷，填写者必须登录后作答。当前实现的主要功能如下。

| 功能模块 | 已实现内容 |
| --- | --- |
| 用户管理 | 注册、登录、退出、查询当前用户，按创建者隔离问卷 |
| 问卷管理 | 创建和修改草稿、发布、生成填写链接、设置截止时间、关闭收集 |
| 题目管理 | 单选、多选、文本和数字四类题目，草稿内添加、修改和删除 |
| 规则处理 | 配置必答与题型限制，支持单选、多选、数字条件跳转 |
| 回答管理 | 逐题填写、返回修改、最终校验、匿名提交和重复填写控制 |
| 结果统计 | 查看整体或单题统计，包括选项次数、文本内容和数字平均值 |

## 二 系统设计与实现

### 2.1 系统架构与技术选型

系统由浏览器、Flask 后端和 MongoDB 组成。浏览器通过页面收集输入，JavaScript 调用 JSON API，后端执行业务判断后通过 PyMongo 访问数据库。页面由 Flask 模板生成，与 API 同源运行，减少了课程项目中额外部署前端服务的工作。

```text
浏览器页面 → Flask 路由 → 数据模型与业务逻辑 → PyMongo → MongoDB
```

选择 Flask 是因为其路由组织较直接，便于按功能拆分和使用测试客户端验证；PyMongo 能让代码中的读写操作与文档结构对应。前端负责交互，服务端负责最终判断，避免仅靠隐藏按钮或输入框限制维护业务规则。具体安装和启动方法见 [README](../README.md)。

### 2.2 模块划分与设计考虑

| 模块 | 主要职责 | 划分考虑 |
| --- | --- | --- |
| 用户认证 | 注册、密码哈希、登录和会话 | 统一识别请求身份，为权限检查提供依据 |
| 问卷与题目管理 | 配置、题目和规则维护 | 集中检查创建者权限及草稿可编辑条件 |
| 跳转与答案校验 | 判断单题答案、计算实际路径 | 让逐题接口与最终提交复用同一套判断 |
| 回答提交 | 保存、去重和中断恢复 | 把数据保存问题与页面展示分开 |
| 统计 | 根据正式回答汇总结果 | 保持统计与原始回答之间的对应关系 |

系统将请求处理、数据访问、单题校验和路径计算分开，主要是为了让网页与最终提交复用同一套业务判断。路由负责会话、请求格式及返回，模型负责数据读写，校验器和跳转引擎处理规则，出现问题时更容易定位，也便于独立测试。代价是模块之间需要维护一致的字段和错误约定；例如只修改页面校验而未同步最终提交，就可能出现行为不一致。因此 next 与 responses 共用路径校验，而不是各写一套。

这种划分提高了可读性和复用性，也增加了模块间的调用关系，需要保持字段格式、异常和权限约定一致。对目前的项目规模，我认为适当拆分比把所有功能集中在一个文件中更便于定位问题，但也没有必要为每个小操作增加单独的层次。

## 三 MongoDB 数据库设计

### 3.1 集合划分与数据组织

本项目使用 MongoDB 作为数据库，默认数据库名称为questionnaire_system。在设计数据库时，我没有将每种数据都单独建立一个集合，而是结合数据之间的关系、查询方式和数据增长情况，将系统划分为 users、surveys、responses 和 participations 四个集合。

| 集合 | 主要存储内容 | 设计目的 |
| --- | --- | --- |
| users | 用户账号、密码哈希、注册时间 | 管理用户身份和登录信息 |
| surveys | 问卷基本信息、题目数组、发布状态及填写设置 | 集中管理问卷配置 |
| responses | 问卷 ID、填写者标识、答案及提交时间 | 保存每次有效提交，支持统计 |
| participations | 问卷 ID、用户 ID、参与状态及提交关联信息 | 控制重复填写，并支持提交过程恢复 |

四个集合通过 _id、ownerId、surveyId、respondentId 等字段建立逻辑关联。MongoDB 不要求像关系数据库一样为每个关联强制建立外键，因此需要由后端检查 ID 是否有效、关联对象是否属于同一问卷，以及当前用户是否具有相应权限。
这样的划分主要考虑了两点：一方面，用户信息和问卷配置有相对独立的管理需求；另一方面，回答记录会随着填写次数持续增加，不适合一直放在问卷配置中。参与记录则是为了处理重复填写和提交过程中的状态问题而单独设置的。

### 3.2 核心数据结构
本项目的 Schema 不仅包括字段名称，还涉及字段类型、嵌套结构和数据约束。数据库设计需要考虑的不只是数据能否保存，还包括数据之间如何关联，以及后端能否根据这些结构完成问卷填写、条件跳转和结果统计。

#### （1）用户集合 users

用户文档主要包含以下字段：

| 字段 | 含义 |
| ---| --- |
| _id | 用户唯一标识 |
| username | 登录用户名 |
| passwordHash | 哈希处理后的密码 |
| createdAt | 用户创建时间 |

用户名需要保持唯一，因此我为 username 建立了唯一索引。这样可以将重复用户名的限制落实到数据库层面，而不只是依靠注册接口事先检查。需要注意的是，索引会占用额外存储空间，写入时也需要维护索引，因此没有必要为所有字段都建立索引。

#### （2）问卷集合 surveys

问卷文档保存问卷基本信息和完整题目配置。主要字段如下：

| 字段  | 含义 |
| --- | --- |
| _id | 问卷唯一标识 |
| ownerId | 创建者 ID |
| title、description| 问卷标题与说明 |
| anonymousAllowed | 是否允许匿名填写 |
| allowMultipleResponses | 是否允许重复填写 |
| status | 问卷状态，如 draft、published、closed |
| deadline | 截止时间  |
| questions | 嵌入式题目数组 |
| createdAt、updatedAt | 创建与更新时间 |

题目采用嵌入式文档存储。 一份问卷通常需要同时读取题目、选项、校验规则和跳转配置，将这些内容放在同一个问卷文档中，可以减少读取时的额外查询，也方便在草稿阶段统一维护配置。

每道题在数据库中具有独立的 _id、type、title、required、options、validation 和 order 等字段。选择题使用 options 保存选项，其中 value 是程序识别的值，label 是向填写者展示的文字。题目 ID 用于关联回答和跳转规则，order 则控制显示顺序，二者相互独立。


#### （3）回答集合 responses

回答文档主要包含以下字段：

| 字段 | 含义 |
| --- | --- |
| _id | 回答记录唯一标识 |
| surveyId | 所属问卷 ID |
| respondentId | 填写者标识，匿名回答不保存该字段 |
| answers | 实际提交的答案 |
| submittedAt | 提交时间 |

答案通过 questionId 关联题目，并通过 value 保存答案。单选答案为字符串，多选答案为字符串数组，文本答案为字符串，数字答案为数值。回答与问卷分开存储，是因为一份问卷可能积累大量提交记录。若把全部回答嵌入问卷文档，文档会持续增长，也会增加更新和统计操作的负担。独立的回答集合更适合按问卷查询、保存提交记录和执行聚合统计。

#### （4）参与记录集合 participations

参与记录主要用于重复填写控制和提交过程管理。其关键字段包括 surveyId、userId、responseId、status 和 payload 等。

系统通过 (surveyId, userId) 复合唯一索引，限制同一用户在同一份禁止重复填写的问卷中重复建立参与记录。匿名填写和重复填写控制是两个独立设置：匿名回答可以不在 responses 中保存填写者身份，但系统仍然可以通过参与记录控制同一账号的提交次数。

### 3.3 嵌入与独立存储的设计理由
在设计数据库时，我主要根据数据之间的关系和使用方式选择存储结构。题目、选项和跳转规则通常需要与问卷一起读取，因此我将它们嵌入surveys，这样可以减少查询次数，方便统一管理。但题目过多时，问卷文档也会变大。

回答数据会随着填写次数不断增加，因此我将 responses 单独存储，方便查询和统计，也避免问卷文档不断膨胀。不过，这种方式需要后端维护问卷、题目和答案之间的关联。

此外我单独设计了 participations集合，用于控制重复填写和处理提交状态。通过 (surveyId, userId) 复合唯一索引，可以限制同一用户在同一份问卷中重复建立参与记录。这样能够兼顾匿名填写和重复填写控制，但也增加了跨集合数据维护的复杂度。


### 3.4 索引、Schema 与实际数据库操作

| 索引 | 类型 | 对应需求 |
| --- | --- | --- |
| users.username | 唯一 | 防止重复用户名 |
| surveys.ownerId | 普通 | 查询本人创建的问卷 |
| responses.surveyId | 普通 | 按问卷读取回答并统计 |
| participations.(surveyId,userId) | 复合唯一 | 禁重复问卷中同一账号最多一条参与资格 |

索引可以提高查询效率，唯一索引还能限制重复数据，但也会占用存储空间，增加数据写入时的维护成本。因此，我只针对常用查询和数据唯一性要求建立索引。

数据库初始化时，项目使用 $jsonSchema 检查必要字段、数据类型和问卷状态等基本约束。不过，Schema 只能检查数据结构，无法判断所有业务规则。例如，答案是否属于有效选项、跳转目标是否属于当前问卷，还需要由后端进一步验证。为了兼容旧问卷，allowMultipleResponses 没有被设为所有历史文档的必填字段，新建问卷时则由应用设置默认值。

| 实际 MongoDB 操作 | 项目用途与理由 |
| --- | --- |
| insert_one | 创建用户、问卷和回答，分别管理生命周期 |
| find、find_one | 按 ownerId 查询本人问卷，按 surveyId 读取回答 |
| update_one | 修改状态、草稿设置及参与记录状态 |
| find_one_and_update 更新管道 | 一次计算题序并追加完整题目，避免分步写入的中间状态 |
| create_index | 约束用户名、参与资格唯一，并支持常用查询 |
| upsert、$setOnInsert | 使用固定回答 ID 幂等保存首次内容 |

目前统计功能是读取 responses 集合后由 Python 进行汇总，没有使用 MongoDB 聚合管道。这样实现比较直观，也方便检查统计结果；但随着回答数量增加，统计成本可能上升，后续可以考虑使用聚合管道优化。


## 四 跳转逻辑设计

### 4.1 跳转规则的表示与执行

跳转规则保存在源题的 jumpRules 数组中，每条规则包含 condition 和 targetQuestionId。其中 condition.operator 表示比较方式，condition.value 表示比较值。由于规则已嵌入源题，不需要再存一份来源题目 ID。

| 题型 | 支持的操作符 | 含义 |
| --- | --- | --- |
| 单选 | equals | 选中指定选项 |
| 多选 | contains | 已选答案包含指定选项 |
| 数字 | equals、gt、gte、lt、lte | 等于、大于、大于等于、小于、小于等于 |

填写时先校验当前答案，再按规则数组顺序检查，第一条条件满足且目标有效的规则生效；没有匹配规则就进入顺序上的下一题，最后一题结束后返回 None。例如，配置 Q1 选择 yes 跳到 Q3、Q3 大于等于 18 跳到 Q5，回答 yes 和 20 时，路径为 Q1 → Q3 → Q5。

逐题接口 `POST /api/surveys/<id>/next` 接收截至当前的全部答案，从首题重新计算路径，不保存回答。最终提交仍重新走完整路径，因此不能通过修改客户端当前题号或省略必答答案绕过检查。

### 4.2 关键边界处理

| 情形 | 系统处理 |
| --- | --- |
| 多条规则同时满足 | 按保存顺序采用第一条有效规则 |
| 没有规则命中 | 按题目顺序继续 |
| 目标不存在、属于其他问卷或位于前面 | 保存规则时拒绝；引擎也不采用不存在或不向后的目标 |
| 已完成最后一题 | 返回完成标记，下一题为空 |
| 跳过的题目设置为必答 | 不在实际路径上，不要求作答 |
| 提交携带旧分支答案 | 拒绝额外题目，避免无效答案进入统计 |

为降低循环风险，第一阶段只允许向后跳转，完整路径计算还保留已访问检查。前端返回修改时逐步清除后续答案，再请求后端重算路径。目前不支持文本条件、组合条件或直接跳到结束。

## 五 答案校验设计

### 5.1 校验规则设计

校验分为题目配置和填写答案两层。创建题目时先检查限制是否合理，例如最小值不能大于最大值、多选上限不能超过选项数；填写时再由 validate_answer 根据题型和数据库中的配置判断答案。

| 题型 | 主要检查内容 |
| --- | --- |
| 单选 | 必答、字符串类型、答案属于有效选项 |
| 多选 | 必答、字符串数组、无重复选项、全部有效、选择数量上下限 |
| 文本 | 必答、字符串类型、纯空白处理、字符长度上下限 |
| 数字 | 数值类型、有限值、最小值和最大值、整数限制及 BSON 整数范围 |

必答多选单独检查空数组，即使 `minSelections=0` 也不能提交 `[]`。非必答题可以跳过，但提供非空答案后仍需满足限制。文本按字符长度检查；数字明确排除布尔值、NaN 和 Infinity，整数限制允许 18 和 18.0，拒绝 18.5；Python 整数还需在 BSON 有符号 64 位范围内。

### 5.2 校验执行与错误处理

逐题接口与最终提交共用 walk_response_path，在每个实际到达的题目上调用单题校验。逐题模式中，缺少题目键表示尚未回答，系统返回该题；主动跳过可选题则需传入该题键和空值。最终提交检查完整路径，只有全部通过后才进入保存逻辑。

答案不合法时接口返回 HTTP 400 和具体提示，单题错误可附带 questionId，页面将错误显示在题目旁。非法答案不会形成有效回答记录。可选题的空值不进入保存列表，也不增加该题回答数量。由此，规则保存在题目文档中，后端使用统一代码执行，不必针对每一份问卷重写校验逻辑。

## 六 AI 使用过程

本项目早期使用 ChatGPT 理解需求、讨论数据结构和排查错误，后续使用 Codex 桌面应用中的 AI 编程助手检查本地项目、修改代码、补充测试、实现网页前端。开发采用分步骤推进的方式：先明确问题和修改范围，再应用代码，通过运行结果继续检查。

具体见：[查看 AI 使用日志](ai-usage.md)

### 6.1 AI 辅助开发过程

AI 主要参与了以下工作：

| 开发阶段 | AI 辅助内容 | 实际验证方式 |
| --- | --- | --- |

### 6.3 开发中发现的问题与调整

AI 生成的代码并非全部可以直接使用，部分问题只有在实际调用接口或查询数据库后才能发现。例如，添加跳转规则后，通过数据库查询发现同一规则被保存了两次。检查数据后，我清理了重复记录，并进一步认识到接口还需要考虑重复请求时的数据一致性。另一次排查中，问卷标题和题目显示为问号；检查数据库后发现部分中文内容已经被保存为问号，因此通过更新对应字段恢复数据，并重新调用接口验证。
早期测试还发现了 ObjectId 使用错误、测试模块导入失败，以及必答多选题可能接受空数组等问题。后续针对这些问题调整了代码和测试方式，并在后端修复中增加请求参数检查、边界校验及回归测试。

## 八 遇到的问题与解决方法

在系统开发过程中，部分问题是在实际运行、API 调用、数据库查询和边界测试中逐步发现的。针对这些问题，我结合错误信息和实际数据检查原因，再修改代码或数据库内容，并通过重新运行测试验证处理结果。

### 8.1 主要问题与处理情况

| 问题现象 | 原因与处理 | 实际结果及限制 |
| --- | --- | --- |
| ObjectId 使用错误、测试导入失败 | 早期代码使用不支持的 .hex，直接运行测试时模块路径不正确；调整 ID 处理与启动方式 | 历史记录显示基础检查恢复，当前原有回归测试通过 |
| 重复跳转规则 | 同一规则多次请求被追加；清理历史重复数据 | 历史数据清理后仅一条；当前接口仍不自动去重 |
| 中文保存为问号 | 数据库原字符串已损坏；更新对应中文字段后再查询 | 历史 API 复查显示中文恢复，不归因于单纯终端显示 |
| 必答多选空数组 | 通用空值判断遗漏 []；多选分支增加必答检查 | 原有专项校验通过；集成测试非法提交400且回答数为0 |
| 错误请求引发异常 | JSON数组、null标题等未先检查类型；补充输入检查 | 原有回归用例返回400；其他非法ID异常仍未统一处理 |
| 首次初始化 | 原方式假定集合存在；缺失时创建、已有时更新Schema | 原有新建及重复初始化测试通过，保留已有用户 |
| 并发题序 | 分步更新存在中间状态；改为一次更新管道 | 原有四线程12题断言通过，顺序为1～12 |
| 匿名去重 | 匿名回答无用户字段；新增独立参与资格和唯一索引 | 原有匿名后重复提交409，同账号并发仅保存一份 |
| 提交中断 | 两集合分步写入；持久化首次payload并固定回答ID | 原有中断重试和关闭后恢复用例通过，保存首次内容 |


### 8.2 问题处理总结

以上问题涉及不同层面的系统可靠性。ObjectId 和模块导入问题主要影响开发及测试执行；中文数据异常和重复跳转规则涉及数据库中实际保存的数据；必答多选题空数组和非法请求则体现了后端输入校验对边界条件的覆盖程度。后续开发中，系统进一步关注了并发添加题目、匿名填写去重和提交中断恢复等问题。这些问题不能只通过前端限制解决，需要结合 MongoDB 索引、后端业务校验和可重复执行的提交逻辑进行处理。

通过这些排查过程，我认识到，功能能够正常运行并不意味着所有输入和异常场景都已得到处理。因此，项目后续采用先核对现有实现、再集中修改、最后执行回归测试的方式，减少重复修改，并提高最终实现的可靠性。
