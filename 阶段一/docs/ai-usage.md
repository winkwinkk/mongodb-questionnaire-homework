# AI 使用日志、AI 使用说明

## 一、AI 使用日志

### 1. 使用工具与方式

本项目开发过程中使用了 ChatGPT 和 Codex 桌面应用中的 AI 编程助手。ChatGPT 主要用于理解课程要求、讨论数据库设计、解释错误和规划开发步骤；Codex AI 编程助手用于检查本地项目、修改代码、补充测试、实现前端页面和运行自动化测试。

开发过程不是一次性生成全部代码，而是按照“明确需求—编写或修改代码—实际运行—检查结果—继续修正”的方式逐步完成。我会先说明当前需要实现的功能，或把终端报错和运行结果发给 AI；在确认需要修改的文件后，再应用代码，并通过 PowerShell、Python 测试和 MongoDB 查询检查结果。

#### 记录五：答案校验与独立测试

**使用工具：** ChatGPT 和 Python 测试脚本。

**提示词：** “帮助我实现不同题型的答案校验，并编写测试用例。”

**得到的代码：** AI 提供了 `models/answer_validator.py` 和对应测试代码，覆盖单选选项合法性、多选选择数量、必答题、文本长度、数字范围和整数限制等情况。

**是否修改：** 是。

**修改与验证：** 第一次直接运行 `tests/test_answer_validator.py` 时，出现 `ModuleNotFoundError: No module named 'models'`。根据建议调整运行方式后，答案校验脚本中的 12 项检查均显示通过。

在后续开发和检查中，我又发现“必答多选题可以提交空数组”的边界问题。这个问题说明，即使已有测试通过，也可能遗漏特殊输入。因此，后续修复中需要专门检查必答题的空数组情况，并将其加入回归测试，不能只依据早期 12 项测试就认定所有校验逻辑都没有问题。

#### 记录六：条件跳转与规则保存

**使用工具：** ChatGPT、Python 测试脚本和 PowerShell API。

**提示词：** “帮助我实现问卷条件跳转，并编写跳转引擎测试。”

**得到的代码：** AI 提供了 `models/jump_engine.py`、`models/jump_model.py` 和跳转规则路由的实现建议。跳转引擎用于根据回答和规则判断下一道题，规则模型负责保存跳转条件。

**是否修改：** 是。

**修改与验证：** `tests/test_jump_engine.py` 中的 11 项独立检查均显示通过，覆盖单选条件匹配、多选包含、数字比较、无匹配规则时进入下一题以及最后一道题结束等情况。我随后通过 API 添加跳转规则，并使用 `check_jump_rules.py` 查询数据库中的规则。

检查时发现同一条跳转规则被保存了两次。根据查询结果，我清理了重复规则，最终只保留一条。这次问题让我认识到，除了检查规则是否能保存，还应考虑重复请求时的数据一致性；清理已有重复记录并不等于接口已经完全具备防重复能力。

#### 记录七：问卷发布、公开读取和中文异常

**使用工具：** ChatGPT、PowerShell API 和 MongoDB 查询。

**提示词：** “在现有问卷模型和路由中增加发布接口，并实现获取已发布问卷的接口。”发现中文显示异常后，我又提出：“问卷标题和题目显示为问号，请帮我排查并修复。”

**得到的代码：** AI 提供了问卷发布、读取问卷详情的路由实现建议，并建议检查 MongoDB 中实际保存的字符串，而不只是根据终端显示判断编码问题。

**是否修改：** 是。

**修改与验证：** 发布接口返回成功，问卷状态变为 `published`；公开读取接口能够返回四道题、选项和校验规则。但在检查完整 JSON 时，问卷标题、说明和题目文字都显示为 `????`。进一步检查发现，数据库中保存的内容本身已经变成问号，因此不能单纯通过修改终端编码恢复。

随后，我更新了问卷标题、说明、题目标题和选项标签，再次调用接口，确认中文内容恢复正常。这次排查说明，遇到显示异常时需要区分终端编码问题和数据本身已经损坏的问题。

### 3. AI 生成代码后的总体修改情况

AI 提供的代码并非全部直接采用，而是根据实际运行结果进行检查和修改。主要包括修正 `ObjectId` 的使用方式、调整测试文件的运行方式、处理题目参数校验和必答多选题空数组、检查重复跳转规则、恢复中文数据，以及完善后端回归测试和前端页面。

在后续开发中，我也逐渐改变了使用 AI 的方式：不再只要求 AI 提供单个函数，而是先核对已有文件和函数关系，再确定修改范围，尽量集中完成一个完整功能后统一测试，减少重复修改文件的情况。

### 4. AI 使用的局限

AI 生成的代码仍需要结合项目现状和真实测试结果进行验证。开发过程中出现过模块导入错误、重复跳转规则、中文数据异常以及必答多选题空数组等问题。部分早期代码虽然通过独立测试，但在进一步检查边界条件时仍发现了问题。这说明 AI 可以提高编码和排查效率，但不能替代开发者对需求、数据库状态、业务逻辑和测试范围的判断。对于没有实际运行或没有保留测试证据的功能，不能仅凭 AI 给出的代码就认定已经完成。

## 二、AI 使用说明

### 1. AI 帮了什么

AI 帮助我理解大作业要求，规划数据库结构和项目模块，并辅助完成用户认证、问卷创建、题目管理、答案校验、条件跳转、问卷发布、填写接口、重复填写控制、前端页面和自动化测试。遇到运行错误时，AI 也帮助我分析 `ObjectId` 属性错误、模块导入失败、跳转规则重复写入和中文数据异常等问题。

### 2. AI 做错了什么或有哪些不足

开发过程中发现，早期实现存在必答多选题空数组校验不充分、重复跳转规则可能被重复写入等问题；部分代码也需要根据本地文件结构调整。中文内容显示异常时，如果只调整终端显示而不检查数据库原始数据，就无法真正解决已经被替换为问号的数据问题。此外，独立模块测试通过并不意味着完整业务流程全部通过。例如，跳转引擎测试通过，只能说明已覆盖的规则判断场景符合预期，不能单独证明前端填写时的跳转、提交和统计都没有问题。

### 3. 自己修改或验证了什么

我根据课程要求明确项目需要实现的功能，实际使用 PowerShell 调用注册、登录、问卷创建、添加题目、发布和读取接口，并根据错误输出继续排查。对于重复跳转规则，查询数据库确认重复数据并清理；对于中文异常，检查数据库中保存的原始字符串，再更新相应字段并重新调用接口验证。后续后端修复和前端页面的主要代码由 Codex AI 编程助手直接修改。我主要参与需求确认、修改范围控制、对运行结果的检查和反馈，以及重新运行测试。

### 4. 自己设计了什么

本人在需求层面确认填写必须登录、重复填写由创建者控制且默认禁止、匿名为独立开关，并同意在现有项目上扩展。数据库结构和恢复机制是在 AI 建议下采用的项目方案，不将所有技术细节写成本人独立提出。例如，采用问卷内嵌题目的方式组织数据，将回答和参与记录独立保存，以便支持问卷统计、重复填写控制和匿名填写；同时，将题目校验和条件跳转规则作为数据进行保存，而不是将具体规则写死在程序中。此外，我还结合实际测试结果，关注必答多选题空数组、并发提交和提交中断恢复等边界情况，使系统设计不仅满足基本功能，也兼顾数据一致性与后续扩展。

### 5. 使用 AI 后的体会

AI 提高了本项目的代码编写效率，也帮助我逐步理解 MongoDB 数据模型、Flask 后端接口、条件跳转和答案校验等内容。但开发过程也出现了一些问题，局部代码能够运行，并不代表完整流程正确；独立模块测试通过，也不代表所有边界条件都已覆盖。在项目实施中，我主要负责明确课程要求和业务规则、反馈实际运行问题、确认修改范围，并根据 API 调用、数据库查询和测试结果检查实现效果。项目中的具体实现是在需求分析、AI 辅助开发和实际验证相结合的过程中逐步完善的。

通过这次开发，我逐渐形成了先核对现有文件和业务要求、再确定修改范围、最后通过测试验证结果的工作方式。认识到AI 更适合作为辅助开发和问题分析工具，系统是否符合要求，最终仍需依据实际代码、数据库状态和可复现的测试结果进行判断。后续使用 AI 时，我会更加重视先理解现有项目结构、明确修改范围，并在修改后保留可复现的测试证据。
